## Attack 1 — does the replacement test load the code it claims to test?

**Mostly yes — and where not, it is named below rather than hidden.**

`src/lib/spine/the-self-check-must-ask-the-real-schema.test.ts:42` imports `verifyStationOutput`
from `@/lib/spine/driver.server`, and ten `it()` blocks call it for real. This was the specific
fraud in the deleted files ("imported nothing but vitest") and it is genuinely gone: the deleted
`s0-001-end-to-end.test.ts` / `self-check-verification.test.ts` no longer exist and nothing imports
them.

The mock is honest for what it covers: `clientReturning` implements `.from().select().in()`, which
is exactly and only the chain `verifyStationOutput` walks (driver.server.ts:1318-1321, 1344-1347,
1373-1376 at `60dd95e34`). Had the function called any other method, the behaviour tests would
throw, not pass.

**Weakness found, named precisely:** two of the four describes assert on SOURCE TEXT, not
behaviour — "the columns the checks name are the columns that exist" slices `DRIVER` between two
function names and regex-matches `.select("...")` strings (test lines 130-156), and "the self-check
hold is bounded" asserts `body.indexOf('last_hold: "self-check-failed"')` plus a 600-char window
containing the literal `attempts: (row.attempts ?? 0) + 1` (test lines 179-196). That is
grep-in-a-test: the same species as the `pageContent.includes()` failure this repo already paid
for. It pins the string; it cannot prove the write executes when verification fails. It is also
brittle in the safe direction — any refactor that reformats those lines fails the test loudly. I
corroborated both pinned strings against the live call path by hand (see attack 3), so the claims
they carry stand, but they stand on my read, not on the test's execution.

Also noted: no test drives `sense` or `build` (the two checks that were right before the fix and
were left unchanged). Acceptable scope, worth knowing.

## Attack 3 — is the bound real?

**CONFIRMED statically, end to end — with one correction to how S0 described it.**

The chain a failing station actually walks:

1. Station produces this visit → `verifyStationOutput` called only under
   `producedThisVisit && !failed && !haltedAs && !overBudget && !ranLong` (driver.server.ts:2320).
2. On failure the write increments and holds in one statement:
   `attempts: (row.attempts ?? 0) + 1, last_hold: "self-check-failed"` (driver.server.ts:2335-2336).
3. `self-check-failed` is NOT in `TERMINAL_HOLDS` (correction.ts:262-270 = given-up,
   station-cannot-finish, tools-refused, going-in-circles), so track-tick.ts:119-120 still picks
   the track next tick. **The retry happens; this is not a freeze.**
4. `decideDrive` refuses to act once `attempts >= MAX_STATION_ATTEMPTS` (= 3, driver.ts:523) and
   returns hold `stalled` (driver.ts:1037-1038).
5. The held path feeds `stalled` to `correctIfPossible` (driver.server.ts:1600-1611); `stalled`
   IS in `CORRECTABLE_HOLDS` (correction.ts:178-185), so `decideCorrection` runs with attempts=3,
   passes the cheap-retry gate (correction.ts:520), and routes go-back / escalate / give-up per
   the station-needs rule. A success resets attempts to 0 on the move write
   (driver.server.ts:2544-2562), so progress is never taxed.

**The correction to S0's wording:** the commit message and the test comment say "three tries hand
it to given-up". Precisely: three tries hand it to `stalled`, and `given-up` is ONE of four
outcomes of the correction decision (and requires the corrections budget spent AND the need met).
Bounded it is — unbounded it is not — but a reviewer quoting "given-up after 3" would mispredict
escalations. Also verified deliberate: `self-check-failed` stays OUT of `CORRECTABLE_HOLDS`
(joins `RETRIED_UNTOUCHED` in correction.test.ts:59-88, guarded by the HOLD_LINE partition test),
so the correction loop never reroutes a quality refusal upstream. The design reasoning is sound
and the partition test makes the set closed.
