## 1. The value metric, in one paragraph

Tiers are credit-priced, so credits meter consumption. Memory is what makes the ladder mean something, because it is the only dimension where the product is worth more to the fifth person in a workspace than to the first. The step-ups are triggered by a change in the customer's situation, not by a capability withheld from the tier below: **the second person** triggers Business, and **a departure or an audit** triggers Enterprise. The commercial consequence, which is the line to argue: a team seat is worth more than N solo seats, because judgment compounds across people rather than per person.

The reason this is a durable metric and not a packaging trick: **the record is generated by running the loop**, so it is unique to the customer and it grows with use. That is why memory sits at the centre of the ladder rather than in a feature row, and why a frontier model release changes what the product can do with the record without changing who owns it.

## 2. The ladder

Slugs are canonical (`src/lib/entitlements.ts`); display names are a skin. `max` is a legacy internal slug, not a public tier.

| Slug | Display | The memory promise on the page | Status |
| --- | --- | --- | --- |
| `free` | Free | Your own memory. The recall cache rolls on a 30 day window and then fades. The decision record itself never expires and exports forever. | **[PROVEN]** `FREE_MEMORY_RETENTION_DAYS`, single expiry cron on `agent_memory` only |
| `pro` | Pro | Your own memory, kept. No expiry. Recall pools across all of your workspaces. | **[PROVEN]** `memoryPersists`, `crossWorkspaceMemory` resolved per account tier at recall time |
| `max` | Pro (legacy) | Same as Pro. Not on the public page. | **[PROVEN]** |
| `team` | Business | One shared memory for the whole workspace, with authorship attached to every entry, on both recall paths. The only tier that can accept a claimed workspace from an individual. | **[WIRING]** mechanism applied 2026-08-02 and enforced in SQL, never run by a real team. The tier gate on claiming is **[PROVEN]** |
| `enterprise` | Enterprise | Cross-workspace org brain under policy: retention rules, legal hold, audit export, data residency, SSO, SCIM, and admin visibility into what the brain knows and who contributed. | **[ROADMAP]** none of it built |

**Single-seat tiers are single seat, and that is enforced, not assumed.** `entitlements.seats` is 1 for free, pro and max, and null (many) for team and enterprise, with a drift guard pinning the SQL seat limit to the same source. This is what makes the packaging honest: on a single-seat tier, workspace sharing is a **no-op rather than a withheld feature**, because there is no second person in the workspace. The base product carries the whole promise for a solo product manager, and nothing is hollowed out to manufacture an upgrade.

## 3. What the 2026-08-02 changes actually moved

Five migrations and one feature, all applied to production and verified there on the day.

**a. Shared by default, with immutable authorship.** Migration `20260802190000_agent_memory_workspace_visibility.sql`:

- `agent_memory.visibility`, constrained to `workspace` or `private`, **defaulting to workspace-shared**. **[PROVEN]**
- RLS split into read and write. Read reaches a teammate's shared memory within a workspace you belong to; write, update and delete stay restricted to the author, so authorship is immutable. **[PROVEN]**
- Semantic recall (`match_agent_memory`) made workspace-aware on both the authenticated path and the service-role path the agent loop and crons run on, via a new `user_in_workspace(workspace_id, user_id)` membership check that works with no session. **[PROVEN]**

**b. The second recall path, which the first migration missed.** Migration `20260802191000_reflections_workspace_visibility.sql` applies the identical shared branch, including the service-role membership check, to `recent_agent_reflections`. **[PROVEN]**

_Packaging consequence: the row in §4 that said reflections were still author-scoped is closed and has been removed. Copy may now say the workspace shares one memory, without a footnote about which half._

**c. The graph now carries the reasoning.** Every lineage edge exposes its rationale and the agent that authored it, recorded outcomes carry their verdict (an unread verdict stays blank rather than defaulting to a good one), belief revisions are dated and carry a confidence tier, and a revision that a later outcome reversed stays visible as history rather than being deleted. **[PROVEN]** This is the packaging justification for selling the brain as a record rather than a diagram.

**d. A correctness fix, and the vocabulary behind it.** 35 of 51 revision edges were being read backwards, because two writers stored the same fact from opposite ends and the read layer only understood one voice. The relation vocabulary had forked into sixteen strings for about thirteen meanings. Fixed at read time (family plus an `inverted` flag, the stored string never rewritten) and at rest (migration `20260802260000_artifact_lineage_canonicalise.sql`, 404 edges before and after, zero old spellings left). **[PROVEN]** Relevant to pricing only because it is the evidence a technical buyer should be shown when they ask whether the record can be trusted.

**e. The workspace claim, which is the departure motion and therefore a packaging object.** Migration `20260802270000_workspace_claim.sql` plus `src/lib/workspace-claim.ts`, `src/lib/workspace-claim.functions.ts` and a Settings surface. **[PROVEN]** as a mechanism, **[WIRING]** as an outcome.

- Two-sided consent: the workspace owner offers, an owner or admin of the destination organisation accepts.
- An inventory of exactly what changes hands is shown before consent, counting signals, themes, opportunities, specs, decisions, learnings, lineage links, shared memories, and private memories listed separately as kept private.
- An unanswered offer expires in 14 days. The claimant keeps a 7 day window to take it back on their own. The organisation can divest at any time after that.
- An owner or admin can see every claim touching their organisation, including offers declined and workspaces released, with who and when.
- **The destination account must be `team` or `enterprise`**, checked in the RPC and in the pure policy layer, because a single-seat plan cannot hold a second person's workspace. **This is the packaging point: the claim is not a feature behind a paywall, it is the reason the upgrade exists.** A product manager who ran Pro solo for a year has real accumulated judgment, and the upgrade is the act that makes it the company's.

**f. A tenancy hole closed on the way.** Any workspace owner could previously move their workspace into any account by uuid with no offer, no acceptance, no audit and no seat check. `account_id` is what account-scoped recall pooling reads, so that was a tenancy boundary, not a billing field. A `BEFORE UPDATE` trigger now refuses any account move outside the claim RPCs. **[PROVEN]** Directly relevant here because §5a's cross-workspace pooling question depends on `account_id` being a boundary that holds.

## 4. The gaps that constrain what the page may say

Each of these is a specific reason a pricing line must be softened until it closes.

| Gap | Effect on the page | Status |
| --- | --- | --- |
| **The claim's audit trail does not survive workspace deletion.** It rides on `workspace_audit_log`, whose `workspace_id` is `on delete cascade`. Deleting a claimed workspace erases the organisation's proof of how it acquired the work. | The Enterprise "prove what they knew" line cannot be sold as durable evidence. Say what it does today and name this limit rather than burying it. This is the single largest blocker between the claim and an enterprise pitch. | **[ROADMAP]** |
| No product control for `visibility`. One surface now reads the column (the claim inventory splits shared and private counts), but nothing in `src/` writes it and the generated Supabase types do not carry it yet. | Do not write "choose what stays private". Write "private is supported in the data model" or say nothing. | **[WIRING]** |
| Memory recall does not return the author. The row carries `user_id` and the write rules enforce it, but `match_agent_memory` returns no author column and no surface displays one. | Do not write "see who contributed what" about recall. Write "authorship is immutable and attributable". The claim trail is the one place attribution is displayed, and it may be described. | **[WIRING]** |
| `decisions`, `opportunities`, `prds` and `learnings` carry no embeddings of their own. Semantic recall proxies through `agent_memory`, the only embedded layer. Work in flight. | Do not write "search everything you have decided". The recall promise is scoped to what the agent recorded, not to every artifact table. | **[WIRING]** |
| No team and no organisation has run it. Single-digit users, all founder or internal. | No measured outcome may appear beside the Business line, and none beside the claim. The line names the loss, not a result. | **[WIRING]** |
| The entire enterprise governance layer: retention policy, legal hold, audit export, data residency, SSO, SCIM. | The Enterprise memory line stays off the page, or carries an explicit "in development" marker and a date. | **[ROADMAP]** |

## 5. Open founder calls

**a. The Enterprise line conflicts with what already ships, and this needs a decision before any pricing page is built.** The ratified ladder puts a "cross-workspace org brain" at Enterprise. In code today, `crossWorkspaceMemory` is true for **every paid tier**, and recall already pools across all of an account's workspaces for pro, max and team accounts. So cross-workspace recall is not an Enterprise capability, it is a paid capability. Three ways out, in the order they should be considered:

1. **Redefine the Enterprise line around governance rather than reach**, which is the honest reading of the founder's own list: retention, legal hold, audit export, data residency, SSO, SCIM, admin visibility. Cross-workspace recall stays a paid-tier capability and Enterprise sells policy over it. This requires no code change and no removal of anything a paying customer already has.
2. **Distinguish account-scoped pooling from org-scoped pooling.** Today's pooling is keyed to a billing account, and as of the 2026-08-02 trigger that key is a boundary nobody can move without a consented claim. An org brain that spans accounts, business units or acquired teams is a genuinely different object and could sit at Enterprise without taking anything away.
3. **Move `crossWorkspaceMemory` up the ladder.** Not recommended. It would remove a capability from tiers that already have it, which breaks the no-paywall rule that makes the rest of this ladder credible.

Recommendation: option 1, with option 2 as the expansion path. Either way, "cross-workspace" must stop being the Enterprise headline, because it is already true one rung down.

**b. Where does the workspace claim sit on the page?** It is now the most concrete thing in the memory story: a shipped, enforced, two-sided workflow with an inventory, an expiry, a release window and an admin trail. It gates on Business or Enterprise, so it is a legitimate Business line. The argument for putting it on Business is that it converts the awkward truth of the ladder (individuals expense Pro on a work email) into the upgrade motion. The argument against is that it names a risk the buyer may not have been thinking about. Founder call, and it is the copy decision on this page that moves the most.

**c. Is the Business memory line the primary upgrade trigger on the page, or the second one?** Business also carries write-back connectors, shared credits, roles and approval lanes. The argument for leading with memory is that it is the only one a competitor cannot match by shipping a feature. The argument against is that connectors are the concrete thing a buyer clicks. Founder call.

**d. Does the Enterprise line appear before its wiring lands?** The standing rule says a claim never outruns the wiring, and a pricing page is the strictest surface for that rule. Default is off the page until it ships. If it goes on early, it carries a visible "in development" marker and a date. Note the ordering dependency: the audit-trail cascade in §4 should be fixed before the Enterprise line is written at all, because it undercuts the exact sentence the line makes.

**e. Does memory get its own metered dimension later?** Today credits meter consumption and memory is a tier capability. If retention windows, org-wide recall or export volume ever become metered, that is a pricing-architecture change and belongs in [`pricing-architecture.md`](./pricing-architecture.md), not here.
