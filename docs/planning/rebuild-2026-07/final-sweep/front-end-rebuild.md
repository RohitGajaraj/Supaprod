## 1. Context

Supaprod is an agentic, end-to-end product lifecycle platform: a user brings an idea and the platform's agents carry it through planning, design, build, ship, launch, and go-to-market — with the human approving at defined gates. The backend engine (agent orchestration, reasoning, lifecycle intelligence) is powerful and already validated. The front-end is not. This brief commissions a complete rebuild of the front-end layer — information architecture, screens, design system, copy, and demo data — with authority to make supporting code changes at the backend level where the new experience requires them. It replaces every prior design direction from v1 through v5 (Tempo). This is the **final sweep**: five named design systems and multiple rebuilds preceded it, none fixed the core problem, and there is no seventh pass — every decision is judged against the end state (premium, calm, light, near-zero learning curve, consumer-loved, enterprise-credible), never against precedent or habit.

Timeline: the rebuild completes in the next 2–3 days; the product goes in front of paying customers and into the YC application within ~4. This is a no-compromise build — features, look, and feel all ship at full quality. If the clock ever forces a trade-off, surface it to Rohit as an explicit decision (§16); never silently cut scope or polish. This build is for real customers and for YC — in that order, and the application must speak for itself.

## 2. The Problem, Stated Honestly

The current application fails the ten-second test. A new user — and today, even the founder — cannot tell what the product does, where to start, or why any given section exists. Symptoms:

- **Cognitive overload.** Too many tabs, sections, and parallel interactions — including multiple visible agents whose purposes are unclear. Information density with no hierarchy. The user must spend brainpower on navigating the platform and its agents instead of on their product.
- **The engine is hidden.** The platform's real power (agents, reasoning, lifecycle intelligence) lives in the backend while the front-end surfaces plumbing. Example: the hub shell's *Design* area currently exposes design-system file setup — configuration that belongs to the machine — instead of showing design *work*.
- **Friction contradicts the pitch.** We claim "agentic-first, near-zero learning curve." The interface demands manual steps everywhere. If using Supaprod takes as much effort as the user's existing stack, they have no reason to switch.
- **Five named design systems (v1 → v5 — Ember, Obsidian, Loom, and Tempo among them) have not fixed this,** because each iterated on the same flawed architecture. Tempo gestured at Vercel but didn't land. Treat all five as reference history to mine for lessons, not as a foundation.

The bar for failure: a prospective user who lands here today would not sign up. Demolish that baseline.

## 3. Objective

Rebuild the Supaprod front-end so that a first-time user understands what the platform does within ten seconds, produces something real within five minutes, and moves from idea to launched product through conversation and approvals — never through hunting, configuring, or learning. The governing criterion above all others: a surface so minimal and light that users love it, over an engine powerful enough that everything gets done — executable from one place, and enterable at any stage of the lifecycle. The result must be minimal on the surface, powerful underneath, world-class in craft, enterprise-credible in trust, and architected to stay relevant as frontier models evolve over the next decade.

## 4. Success Criteria (testable — verify each before declaring done)

1. **Ten-second comprehension:** an outsider shown the signed-in home screen can state what Supaprod does, unprompted.
2. **Five-minute first value:** signup → first meaningful artifact (a plan, a screen, a draft) in ≤ 5 minutes and ≤ 3 user decisions.
3. **IA budget:** global navigation ≤ 4 items. Every screen has exactly one primary action. No screen requires horizontal scanning of more than ~7 elements to parse.
4. **Single pull point:** the Approvals queue is the only place a user must check. Nothing essential lives anywhere the user has to remember to look.
5. **Zero stray brand:** no brand use of Cadence — and no wrong spellings of Supaprod — anywhere in UI, code, or docs, judged against Prime Directive 1's ledger exceptions.
6. **Theme parity:** every route renders correctly in dark and light, and the System setting tracks the OS preference (including a live OS switch mid-session).
7. **Journey completeness:** using seeded demo data only, a full walkthrough from login → plan → build → approve → ship → launch assets → GTM checklist works end to end without setup.
8. **Craft floor:** WCAG AA contrast, visible keyboard focus, reduced-motion respected, empty/loading/error states designed for every screen, p75 route interactive < 2s on mid-tier hardware.
9. **Founder demo:** Rohit can demo idea-to-launch in under 5 minutes without notes, following the demo script you deliver (§17).
10. **Justification ledger:** every screen and major component carries a one-line job annotation, compiled into a reviewable ledger.
11. **Backend integrity:** the pre-existing backend test suite stays green after all changes; anything modified gains new or updated tests.
12. **Any-stage entry:** "design a mockup" and "add a feature to my existing product" both reach useful work directly, without passing through unrelated lifecycle stages.
13. **Context-native canvas:** generated code renders in a Codex/Cursor-grade code-and-terminal view; design work renders as live previews; the canvas adapts to the work automatically, with zero user configuration.
14. **Orientation at a glance:** at any moment, the user can answer "where am I, what's happening, what needs me, what's next" from what is already on screen — the project spine reads as a journey map from idea to launch, and Home always offers exactly one obvious way to begin.
15. **Zero orphaned capability:** the capability coverage matrix (§7) accounts for every feature the platform has today — each reachable via the command surface, its spine stage, or a progressive-disclosure door, or explicitly retired with Rohit's sign-off. Lighter never means less capable.

## 5. Product Thesis — USP and Moat (this must be *felt* on screen, not written in a tagline)

**Positioning (updated 2026-07-18, founder ruling — supersedes older phrasings such as "the decision and outcome operating system").** Supaprod is the **end-to-end product management operating system** — native, agentic-first, one OS where the entire product lifecycle runs. Its sharpest claim: **it tells you what to build.** Building software is commoditized — code is cheap and getting cheaper — so deciding what to build is now the highest-stakes act in product work, the one call that cannot go wrong. Nobody else makes that call today; it sits in the product manager's head, assembled from scattered documents, market reads, and gut feel. Supaprod makes it from evidence — market signals, competitor moves, user feedback, your own product's data — and the human approves it; then its agents carry it through planning, design, build, ship, launch, and growth without a hand-off. And it learns while it works: your product, your taste, your conventions, how your product is evolving — so its judgment about *your* next what-to-build compounds with use (the Memory Brain, §11). Category claims, in order: the agentic **product operating system for product teams** (end to end), the **what-to-build decision layer**, and the **memory layer** as a first-class capability. Every piece of messaging, in-app and on the landing page, carries this story.

**USP: it answers "what to build" — then executes the entire lifecycle in one place.** No competitor tells you what to build. Today that decision lives in the product manager's head: trawling documents, market research, user feedback, and competitor moves, then making a judgment call under heavy cognitive load — slow, expensive, sometimes right, sometimes wrong. Point tools assist slices of the work; the decision itself has no owner. Supaprod owns it — it derives what to build from evidence (your market signals, competitor movements, user feedback, and your own product's data), presents the call with its reasoning for the human to approve, and then never hands the user off. Planning, design, code, shipping, launch copy, GTM — agents execute all of it natively by orchestrating whichever frontier models are best for each job, drawn from the platform's full model catalog (any provider, swappable overnight), through the platform's own keys by default. The user never *needs* to bring an API key, open Cursor/Devin/Windsurf, or leave. (Users never see or think about API keys at all — the only unit a user ever touches is **credits** (§12); the platform's own provider accounts power everything underneath. Bring-your-own keys exist solely as an enterprise-negotiated option, and even then only for restricted execution areas: the judgment core — judge, eval, and decision calls — always runs on the platform's own routing, which the backend already enforces.)

**Moat, in layers:**
1. **Workspace memory — the Memory Brain.** Every approval, rejection, and edit teaches the workspace. Decisions, taste, and conventions accumulate — switching away means abandoning a system that already knows how this team builds. (Full treatment in §11; today this exists mostly in name, and fixing that is a core deliverable of this rebuild.)
2. **End-to-end context.** Because Supaprod sees plan → build → launch → results in one graph, its agents make better calls than point tools that see one slice.
3. **Model-agnostic orchestration.** The experience contract is stable while models underneath are swappable. When better models ship, Supaprod gets better overnight — users feel compounding improvement without migration. This is the ten-year design.
4. **Trust rails.** Approval gates, audit trails, and role controls make autonomy safe enough for enterprises — the hardest thing for agent products to earn.

Every screen should quietly reinforce one of these four. If a screen reinforces none, question it.

## 6. Experience Principles — laws every screen obeys

1. **Intent in, artifact out — from one place.** The user says what they want; the system returns finished work plus a decision, never a form to fill. Every capability is reachable from the command surface: users execute from one place and never tour sections to discover what they do. Sections exist to review work, not to find features.
2. **Agents move by default; humans decide at gates.** Autonomy with brakes, not steering wheels. Gates exist only where judgment, spend, or irreversibility genuinely require a human.
3. **Human brainpower is reserved for product craft.** Taste, priorities, positioning, final calls — those get rich review surfaces. Everything mechanical (setup, config, file plumbing, dependency wrangling) is invisible backend work.
4. **Show state, not machinery.** Users see progress, results, and reasons. They never see design-system file setup, model names mid-task, or orchestration internals — and they never manage a roster of agents: however many run underneath, the user experiences one coherent system doing the work. (This retires the current Design-section failure: the Design area shows only design *work* — screens, components, review states. System configuration moves behind the curtain.)
5. **Anticipate.** The next likely need is pre-staged before it's asked: shipped yesterday → launch copy is already drafted this morning. Prediction is presented as a quiet, dismissible suggestion — one, not a feed.
6. **Everything essential is flagged; nothing essential must be found.** One approvals queue. One notification discipline. Zero "did I miss something?" anxiety.
7. **One primary action per screen.** Secondary actions exist but recede. If two actions compete, the screen splits or one demotes.
8. **Fast is a feature.** Stream agent output. Optimistic UI. Perceived latency is a design material.
9. **Calm density.** Vercel-grade: precise, quiet, engineered. Delight comes from rhythm, motion, and responsiveness — never from ornament.
10. **Ten-year rule.** Models, providers, and capabilities will change; the interface contract (intent → plan → execution → gate → artifact) must not. Design the shell so new capabilities slot into the same loop rather than adding new tabs.
11. **Feels small, does everything.** The interface never displays its full capability up front; depth reveals itself exactly when intent calls for it. The emotion to engineer, again and again: *"wait — it does that too?"* Surprise comes from power appearing on demand — never from features shouting for attention, and never at the cost of the low learning curve. However much the platform grows, it must still *look* like almost nothing.

## 7. Information Architecture — the three-surface model

Collapse today's tab sprawl into three surfaces plus a minimal shell. You may refine naming and boundaries, but any alternative must be *simpler*, not busier, and you must log the reasoning.

**Surface 1 — Home.** The daily entry point, replacing the current "Today" section. One conversational command bar as the hero ("What are we building?"), recent projects beneath as quiet cards, and at most one proactive suggestion. The command bar accepts intent at any lifecycle stage — "plan a habit tracker," "design a mockup for our checkout," "add SSO to my existing app," "write the launch post for v2" — and routes each to the right starting point (§8, Entry at any stage). No dashboards, no widget grids. If ambient touches (date, a single status line) survive the justify-or-cut test, they may exist as one quiet line — the previous weather/focus-dock widgets do not return as widgets.

**Surface 2 — Project.** Where the lifecycle lives. A persistent conversation/command rail; **the adaptive canvas**; and a visible agent-activity timeline so autonomy is legible ("what the agents did while you were away"). The adaptive canvas is one canvas with many faces — it dynamically renders the native representation of whatever the agents are producing, with zero configuration: code generation appears as a Codex/Cursor-grade code-and-terminal surface (streaming Geist Mono output, syntax highlighting, file context, diffs); design work appears as live rendered screen previews; a plan appears as a clean, readable document; shipping shows deploy state; launch shows the actual assets. The canvas switches automatically as the work changes, and the user can pin or flip views at will — this is how the app feels tiny while doing everything. Two working modes, echoing the intent→execution loop (inspired by, not copied from, Lovable's plan/build): **Plan** — the agent drafts scope, spec, and approach for human judgment; **Build** — agents execute across design, code, and content with streaming progress. Lifecycle stages (plan → design → build → ship → launch → grow) appear as a single progress spine within the project, not as separate app sections. The spine doubles as the user's journey map — always visible, showing the whole path from idea to launch: what's done, what agents are doing now, what comes next, and where the user stands. For a live product the spine reads as a loop, not a line — stages re-open as signals and new intents pass through them (§8, "A living product"). Selecting a stage opens that stage's work. A user wondering "where am I, and what happens next?" should be answered by the spine before the question fully forms. Each stage surfaces its star capability *in the stage where it's used*.

**Surface 3 — Approvals.** The single queue of everything awaiting human judgment: plan sign-offs, spend confirmations, deploy gates, copy reviews. Each item shows what the agent proposes, why, cost/impact, and one-tap approve/reject/edit. This queue is the answer to cognitive load: the platform brings decisions to the human; the human never patrols the platform.

**Shell.** Project switcher, Approvals (with count), Settings, account. Nothing else at global level. Settings absorbs workspace, billing, members, integrations, connected tools, personal preferences (theme, notifications, focus modes), the usage meter (§12), and the Memory view (§11) behind progressive disclosure — the calm home for everything that is about the user's account and workspace rather than the work itself. Utility features that live outside the three surfaces today (focus mode, tools, and the like) are not dropped: each lands in Settings, in the command surface, or in the stage where it is used, and the §7 coverage matrix accounts for every one.

**Demotions to backend (invisible):** design-system/file configuration, model selection and routing, environment plumbing, dependency management, agent tooling setup. If it's machinery, it's not a screen.

**Namesake sections die or earn their keep.** Today's Design area, and any standalone Ask/chat tab, exist more in name than in function. Design is rebuilt as pure execution-layer work — screens, components, review states — living inside the Project lifecycle spine; if it cannot justify a standalone home even there, fold it. A separate Ask tab dissolves entirely: conversation is the whole interface, not a destination. Apply this test to every current section — justify-or-cut governs sections, not just buttons.

**Nothing goes orphan — the coverage guarantee.** Justify-or-cut governs *surfaces*, never *capabilities*. The platform today does real work across dozens of routes — discovery, PRDs, roadmap, build, ship, launch, growth, plus deep layers like the Memory Brain, the Pulse signal feed, traces, evals, guardrails, and drift — and this rebuild loses none of it. Killing a screen is fine; killing what the engine can do is not. Every existing capability must stay reachable in the new IA through at least one of: the command surface (ask for it and it happens), its lifecycle stage on the spine, or a progressive-disclosure door that opens on demand. The §11 Memory view is the model for depth: invisible by default, felt through evidence lines in the flow of work, one calm place to inspect it when a user wants to — never the whole brain dumped on screen, never the brain hidden beyond reach. Deep engine surfaces (traces, evals, guardrails, drift) follow the same pattern: the agent-activity timeline is their everyday face; the full instrumentation lives one deliberate door deeper, where power users and enterprise buyers can find it. Phase 1 delivers a **capability coverage matrix** — every current feature and surface → where it now lives → how a user reaches it → what shows by default vs. on demand — and any capability the matrix would truly retire is a §16 flag for Rohit, never a silent cut.

## 8. The User Journey — end to end (each step lists: job · primary action · agent behavior)

1. **Landing/Auth.** Job: state the value in one line and get the user in. Inherits the public site's ink/engineering-grid/starry language exactly. One sentence, one auth block (SSO/social + email), zero clutter. No feature tour.
2. **Onboarding (≤ 3 steps, conversational).** Job: create the workspace and first project from a sentence. The agent asks what they're building; the answer becomes the project; the agent immediately begins a draft plan. No empty states on day one — the user's first screen already contains work in motion.
3. **Home.** Job: resume or start. Primary action: the command bar.
4. **Project · Plan.** Job: turn intent into an approved plan. Agent drafts scope/spec/milestones; user reviews, edits in place, approves. This is a *product-craft* surface — generous, readable, built for judgment.
5. **Project · Build.** Job: watch work happen and unblock it. Agents execute (design, code, content) with streamed progress on the canvas; anything needing judgment routes to Approvals. Human steps here should be near zero.
6. **Ship.** Job: one action to production. Preview → approve → shipped, with environment plumbing invisible and a clear rollback affordance. (Flag: confirm the backend's deploy targets — §16.)
7. **Launch & GTM.** Job: the platform doesn't stop at shipping. Agents pre-draft the launch kit — announcement copy, changelog, social posts, positioning one-pager, GTM checklist — the moment ship succeeds. User reviews and fires. This stage is a core USP; give it first-class treatment, not an afterthought tab.
8. **Grow.** Job: close the loop. A calm digest (adoption signal, feedback themes) with one suggested next move, feeding the learning system. No analytics jungle.

**Entry at any stage — the lifecycle is a spine, not a rail.** Users will not all start at journey zero. Design every entry point below as first-class, never as a degraded version of the full journey:
- **Mockup-only.** "Design a mockup for X" opens a project directly in design work — no forced planning stage; the agent infers a lightweight brief and keeps it editable.
- **Existing product.** "Add these two features to my app" starts with import — connect a repo or URL, agents ingest the codebase and product context, then open directly in Plan or Build scoped to just those features. Earlier stages display as *imported/inferred*, never as fake progress or nagging incompletes.
- **Launch-only.** A product built elsewhere can enter at Launch & GTM for the launch kit alone.
- **Anywhere in between.** The router infers the stage from intent; the user can also reposition on the spine explicitly. Skipped stages are backfilled by agents on demand (e.g., infer a plan from an existing codebase) or marked not applicable.
The rule: the platform meets the user at their stage; it never marches them through stages they didn't come for.

**A living product, not a one-way journey — continuous signals and change injection.** Reaching launch does not end a project; it begins its life. The spine is a *loop*, not a conveyor: any stage can become active again, at any time, without ceremony.
- **Continuous signals.** Connected sources — mail, Jira, the sales pipeline, support, analytics, and whatever tomorrow brings (the connector platform already exists for exactly this) — feed signals in at any point in the lifecycle, not just during Discover. The user never sees a raw firehose: agents triage, cluster, and rank signals in the background and surface only their *conclusions* as proposed work ("a dozen signals this week point at checkout friction — proposal: redesign the checkout flow"), arriving through the same two calm channels as everything else: the single quiet suggestion (Home or the project digest) or, when action is proposed, an Approvals item. The underlying signal evidence sits one door deeper for anyone who wants to inspect it.
- **Change injection.** "Rework the code we shipped six months ago," "redesign this mockup," "that ticket just became urgent" — whether typed into the command bar or born from a signal, a change is simply *new intent on an existing project*. The same router behind entry-at-any-stage scopes it; the relevant stage lights up as active again; agents pull the original context from the Memory Brain and the repo; the work runs as a scoped pass through that stage (and onward if it needs to — build, ship), gated in Approvals like everything else. History is never overwritten: each pass is a recorded cycle on the spine, so the project accumulates a legible life story instead of a frozen timeline.
- **The primitive that keeps this future-proof:** everything — an inbound signal, a typed request, a scheduled follow-up, tomorrow's unknown use case — reduces to **(signal or intent) → agent proposal → human gate → scoped execution pass on a stage.** New capabilities slot into this loop; they never earn a new tab (§6.10).

**The full motion set — design for every direction, not just forward.** Code rework and mockup redesign are only instances. Before any screens are built, the architecture must hold a designed answer — never an assumption — for every motion a real product's life takes on the spine: **interrupt** (urgent work lands mid-pass), **break** (a build, deploy, or agent fails mid-pass — the pass pauses visibly, the reason reads in plain words, recovery options are offered; failure is a first-class state, never a dead end), **go back** (re-open an earlier stage, scoped), **revert** (roll back something shipped, one clear affordance, history intact), **fast-forward** (skip ahead; skipped stages marked inferred or not-applicable, backfillable on demand), **fork** (branch a variant to explore an alternative in parallel — compare, then merge or discard), **pause / resume** (park work, pick it up later with context intact from the Memory Brain), and **cancel** (abandon a pass cleanly, the decision and its reason recorded for the learning loop). Every motion must reduce to the same primitive above and leave a recorded cycle behind — if a motion doesn't fit, the framework is wrong, not the motion. Phase 1's architecture deliverable includes this **lifecycle motion map**: each motion, its user-facing affordance, and its agent behavior, settled before pixels.

**The product-management lifecycle map — cover the domain, not just the build path.** The spine's six stages compress a much richer discipline, and the motion map covers mechanics, not domain. Phase 1 therefore also maps the full product-management domain onto the design: discovery research and user interviews, opportunity framing and prioritization, roadmapping, requirements and PRDs, design, build and QA, launch and GTM, growth and adoption, metrics and outcome review, stakeholder communication, iteration, and eventually sunset/retirement. Every practice and artifact a real product team runs must have a designed home — its spine stage, the command surface, or a progressive-disclosure door — under the same no-orphan rule (§7). This is the category claim (§5, the end-to-end product management operating system) made literal, with a simple test: if a working PM would have to leave Supaprod to do any part of their job, that part isn't mapped yet.

## 9. Design Language — codename **Ink** (design system v6)

**Source of truth:** the public landing site's theme supplies the tokens, type, and temperament (ink / engineering grid); the Vercel reference screenshots collected in the repo's design report supply the product-surface benchmark. In Phase 0 (§13) you extract exact tokens from both. Where the landing site and this section conflict on tokens or feel, the landing site wins. Inheriting the language does **not** mean replicating the landing's texture inside the app — the starfield belongs to the public site and the auth doorway, not to signed-in screens (see Color below).

**Inspiration library (study, don't copy):** the Vercel product and site are the primary reference — revisit the screenshots documented in the repo report and their live product. Alongside them, the craft references Rohit follows — Devouring Details and Interface Craft — and world-class benchmarks like Linear, Arc, and Dia. Mine all of these for interaction details, motion timing, and the user psychology behind why their surfaces feel effortless, and think from every angle: what world-class products do, what users feel, what agents need. Distill the lessons into a one-page **taste document** in Phase 0 that guides every subsequent decision. Inspiration means principles and standards — never lifted pixels, cloned layouts, or copied content. And this list is a starting set, not a boundary: research beyond it. Study the products customers have genuinely, demonstrably loved — whatever the category — and work out *why* they were loved: the onboarding that felt like nothing, the defaults that felt psychic, the one detail that made people show a friend. Bring those patterns home. Rohit's references are the baseline he trusts; your own judgment, fed by that research, is expected to go further (Prime Directive 8).

**The bar for Ink:** today we reference Vercel; tomorrow, founders building their own applications should reference *this* design system. Build and document Ink to publishable quality — tokens, components, interaction patterns, and principles written up as if the system itself will ship as a public reference. Every interactive element gets considered hover, focus, and press states; interactions feel tactile; animation stays subtle and purposeful; and light and dark modes are each crafted as first-class expressions of the same system, not one derived from the other.

**Explicit supersessions from v1–v5** (retired unless the landing site itself uses them): liquid-glass effects, decorative gradients, widget-grid layouts, and the Tempo component skins. Mine v4 Loom and v5 Tempo only for *lessons* (what felt clean, what flowed), never for pixels.

**Direction:**
- **Color.** Dark-first: near-black ink surfaces, hairline borders, high-contrast type, one accent maximum (taken from the landing site). The starry texture stays where it is loved — the public landing and the auth doorway. Inside the signed-in app the default is calm ink with no starfield. Whether any single in-app moment earns the texture is the designer's call, made with world-class judgment *before* building: decide from taste and the references, don't prototype whole screens to find out, and don't route the choice to Rohit — he has delegated this taste call entirely. The bar is premium and elegant, something customers absolutely love; ornament is not the bar. Never wallpaper, never a default. Full light mode: paper-white inversion on the same semantic tokens, equal craft, not an afterthought. Ship three theme settings — **Dark, Light, and System** — with System following the OS preference exactly as the app behaves today. System is the default; dark remains the brand-forward design target.
- **Grid.** The "engineering grid" is structural, not decorative: a strict baseline grid, aligned hairlines, and spacing that reads as machined. Structure should encode meaning — dividers and labels mark real boundaries in the content, nothing ornamental.
- **Type.** Geist Sans for UI, Geist Mono for agent output/data/logs, Geist Pixel *sparingly* as the brand signature (wordmark, stage markers, one hero moment). Deliberate scale, generous line-height in reading surfaces, tight in dense ones.
- **Components.** Cards only where grouping is real; Vercel-grade tables and lists; a Codex/Cursor-grade code-and-terminal surface for generated code (streaming Geist Mono, syntax highlighting, diff views); live rendered previews for design work; skeletons that match final layout; toasts that confirm in the exact words of the action taken.
- **Motion.** 150–250ms, ease-out, purposeful: state changes, streaming text, approval confirmations. One orchestrated moment (e.g., plan → build transition) is the signature; everything else stays quiet. Respect reduced-motion.
- **Signature element.** Choose one memorable, ownable element that embodies "agents at work" — e.g., the live agent-activity spine rendered in Geist Mono on the engineering grid. Spend the design boldness there and keep everything else disciplined.
- **The mirror rule.** Before finalizing any screen, remove one element. If nothing can be removed, look harder.

## 10. Voice and Copy — words are design material

- **Made by humans, for humans — the anti-AI-slop gate (hard invariant, PD 8).** Every word must feel written by a human who cared, never generated. No em/en dashes as stylistic tics, no AI-tell vocabulary ("delve," "leverage," "seamless," "unlock," "elevate," "robust"), no listy three-things-in-a-row patterns, no hedging filler, no "I hope this helps"-register anywhere. Sentences read like a sharp product writer wrote them once and meant every word — plain, direct, specific, occasionally imperfect the way real writing is. Read every string aloud before it ships; if it sounds like it came out of a prompt, rewrite it. Applies to UI copy, empty states, errors, onboarding, launch-kit templates, the copy deck, and landing-page proposals alike.
- **Verbs over nouns.** "Ship it," "Approve plan," "Draft launch post" — never "Deployment Management" or "Content Generation Module."
- **Outcomes over machinery.** "Your launch post is ready," not "Content generation task complete." Model names, agent jargon, and orchestration terms never appear in primary UI.
- **Consistent action vocabulary.** The button that says "Ship" produces a toast that says "Shipped." One name per action across the whole product.
- **From the user's side of the screen.** Name things by what people recognize and control, not by how the system is built.
- **Empty states teach in one line and offer one action.** Errors own the problem, say what happened, and offer the fix — never vague, never apologetic filler.
- **Desire and stickiness through receipts, not adjectives.** Show value earned: "Agents completed 14 tasks while you were away." "Idea to shipped in 3 days." The product proves itself; copy never brags.
- **Naming pass.** Every section, feature, and concept gets a deliberate, human name — deliver a naming table (old → new → rationale), the product one-liner, and a one-liner per surface. Names and taglines are design-system components; anything named "for the namesake" is renamed into meaning or removed. The pass includes the public landing page's messaging — headline, one-liner, and category story aligned to the §5 positioning — prepared as proposals for Rohit's approval per Prime Directive 6, never applied directly.
- Deliver a **copy deck** (all primary UI strings, section names, one-liners, empty/error states, onboarding script, launch-kit templates) as a build artifact so wording is reviewable in one place.

## 11. Intelligence Layer

**Model orchestration (product feature).** A backend router assigns every task to the cheapest model that clears its quality bar, escalating on complexity or failure — automatically. This spec deliberately names **no models and no vendors, anywhere**: the platform already carries a large model catalog (50+ today) behind its gateway, the catalog changes constantly, and the actual models serving it may not be the ones anyone would guess — so verify the real catalog through the backend/gateway in Phase 0 instead of assuming. The runtime treats every model as an interchangeable entry in a **registry that maps models to capability classes** (with eval scores); no task class ever defaults to a hard-coded model. Design to the classes:
- **Fast class** — classification, tagging, autocomplete, quick summaries, microcopy variants.
- **Workhorse class** — standard code generation, drafting, transforms, design-token application.
- **Deep-reasoning class** — multi-step planning, architecture decisions, cross-artifact consistency review.
- **Frontier class** — mission-critical synthesis: full plan generation, pre-ship QA, anything that defines user trust.
- **Auto** — the default posture: the router picks the class per task from task type + confidence, escalates on failure, and switches models freely within a class as availability, cost, and eval scores shift.
Route by task class + confidence; log cost per task; cap spend per task class. End users never pick models; at most they see a quiet "thinking deeper" state. The design is deliberately **hybrid — auto by default, operator override on demand, controlled per surface.** The routing table is keyed by the platform's task surfaces (the `CallSurface` registry already at the AI chokepoint is the natural key): Discover, Build, drafting, deep reasoning, and every other surface gets its own entry, set either to **Auto** — the system classifies and routes, the default everywhere — or to a **pinned model** chosen from the catalog, the way Perplexity exposes per-use model choice, but operator-facing, never end-user-facing. Surfaces that need no model (approvals and the like) are simply marked so. Pins win until removed; Auto resumes when they are; switching is never a per-task human chore. The registry also tracks eval-scored equivalence: when a new model lands that matches or beats a pinned model's benchmark for that surface, it can take the slot — automatically under Auto, as a one-tap suggested swap where pinned. **This control needs a screen — design and build it in this rebuild.** `CallSurface` exists only as a code-level registry today; the product has no routing surface at all. Give the platform operator a **routing console** in the admin area: every surface in one table — current setting (Auto or pin), live cost per task, eval score, latency — and beside each, the system's **recommendation**, continuously computed from benchmarks, eval runs, and cost ("same quality, 40% cheaper"), applied with one tap. Add operator-set policies so the recommendation layer can act on its own where allowed — e.g., auto-adopt an equal-or-better, cheaper model and report afterward — so operating 50+ models never becomes research work or headcount: zero cognitive load by default, the human stepping in only where they choose to. **Who holds this control, by tier:** the platform operator (Supaprod) always, over the full table; end users never; enterprise admins only when their contract includes bring-your-own-keys, and then only for the execution surfaces their keys cover — enterprises without BYOK ride the plan defaults and see no model controls at all, and the judgment core (judge / eval / decision calls) stays on platform routing for everyone, always. Nothing in the UI, the backend, or this build may bake a model or vendor name into the product's structure: the mapping is registry configuration read at runtime, never an assumption in code. A new model or provider tomorrow — any of them — must be a config change plus an eval run, never a rebuild.

**Provider abstraction (the ten-year mechanism).** A capability registry + adapter layer + eval harness so that adopting a new model is configuration plus an eval run — never a rebuild. This is what makes "sustained for a decade" an architecture, not a slogan.

**Native execution — the first-party build engine.** Code generation, preview, and shipping run in Supaprod's own sandboxed execution environment, powered directly by frontier-model APIs. The platform previously leaned on external code-gen engines (Cursor/Devin-class); those hand-offs leave the **default** product flow — out of the box there are no BYO keys and no external IDE detour: the user never leaves, which is the moat made literal. But do not delete capability to get there: the engine-dispatch seam and the enterprise BYO-key chain that already exist in the codebase stay connectable behind the curtain (per Prime Directive 2, working capability is never discarded). Self-serve users only ever see credits — no key concept appears anywhere in their product. Enterprise keys, where negotiated, cover restricted execution areas only; the judgment core (judge, eval, and decision calls) always runs on the platform's own model routing, exactly as the backend enforces today. Default native, optionally open at the edges. The economics support this — inference costs for code generation have fallen sharply and keep falling — but treat that as a hypothesis to verify, not a given: the per-task cost logging above, plus credit pricing (§12), must confirm healthy unit economics with real data.

**Prediction.** Pre-stage the next likely artifact at each lifecycle transition (ship → launch kit; plan approved → first build tasks queued). Always one suggestion, always dismissible, always learned from.

**The Memory Brain — from namesake to moat.** Today the memory brain exists mostly in name; it must become the platform's richest layer, because it is moat layer 1 (§5) made tangible — and a category claim in its own right (§5 positioning). Before designing it, scan the memory-layer landscape — what users ask for, what practitioners say, where the market is heading — and fold the findings into the Phase 0 taste document. Then define it precisely and build to that definition:
- **Purpose:** the compounding context layer that makes every agent smarter about *this* workspace tomorrow than it was today — so output quality visibly improves with use, and leaving Supaprod means starting from zero somewhere else.
- **What it captures:** approved and rejected decisions with their reasons, product facts and positioning, conventions (naming, tone, code style, design taste), stakeholder preferences, and outcomes from shipped work.
- **The brain graph:** structure memory as a connected graph, not a pile of notes — products, features, decisions, stakeholders, conventions, and outcomes as entities with relationships, so context can be traversed, not just retrieved. One unified context layer serves three consumers at once: the **user** (recall, continuity, "why did we decide this?"), the **agents** (task-scoped context injection), and the **system** (prediction, routing, defaults). Everything anyone — human or agent — needs lives in this one place, on this one platform.
- **How it works:** relevant memory is injected into every agent task automatically; it powers the prediction layer and every default. The user never "manages" memory as a chore.
- **How it surfaces:** (a) evidence lines in the flow of work — "Applied your naming conventions from Atlas" — so learning is felt, not claimed; (b) one browsable, curatable Memory view in Workspace settings where users can inspect, correct, or delete what the platform knows. That single view is both the stickiness display (§12) and the enterprise trust control.
- **Claim rule (unchanged):** the UI may only claim learning behaviors the backend demonstrably performs — no "reinforcement learning" or "self-training" language unless literally true. If the current memory backend is thin, you now have authority to design and **build** the enrichment yourself within Prime Directive 2's guardrails — propose the schema in Phase 0, build it, log it. What you must never do is fake depth in the UI. Trust is the enterprise product; inflated AI claims destroy it.

## 15. Review Gauntlet — every screen, dropdown, and micro-interaction must survive all six judges

1. **The outsider power user** (persona of record): expects Vercel-grade craft; allergic to clutter; will churn at the first "where am I?"
2. **The brand-new founder-user:** ten-second comprehension, five-minute value.
3. **The enterprise buyer:** scans for trust — approvals, audit, roles, honest claims.
4. **The investor (YC application reviewer):** the acceptance bar is on the order of one in a hundred, so the product must argue for itself — can the 5-minute demo tell the idea→launch story with zero fumbling, and does every screen communicate problem, solution, and why-now without a human explaining it?
5. **The serial founder** — has built multibillion-dollar, customer-loved products more than once. This judge never asks "does it work?"; they ask what turns users into fans: Is there one moment of genuine delight in the first session? Does every interaction respect the user's time — fast, smart defaults, never asking the same thing twice? Do the details (alignment, wording, transitions, empty states) prove that someone cared? Does the product show its value in receipts, so users brag about it unprompted? Would a customer demo this to a colleague without being asked? *Loved* beats *used* — a screen that is merely functional gets sent back.
6. **Rohit:** would he sign up if this weren't his product? If any judge fails a screen, the screen is not done.
Plus the mechanical sweep: both themes, responsive to laptop-small, keyboard-navigable, empty/loading/error states, perf budget, a11y AA.
