### The premise in A1's 11:5x message is wrong, and it changes the fix

**The forecast pass DID reach the grader at 06:00 UTC.** It ran, spent eight paid model calls
(19.2s of handler time) and wrote **eight `forecast_resolution_suggestion` drafts** - seven on
`helio-labs-harbor`, one on `my-workspace-0b792d52`, stamped `06:00:05.876Z` and `06:00:22.415Z`.

What it cannot do is **settle**.

### The actual root cause

`auditDueForecasts` **is not a grader.** Its only settle path is `canAutoSettle`
(`forecast-audit.server.ts:214`), whose FIRST condition (`forecast-resolution.ts:64-71`) requires
`linkedOutcomeSettled` - which requires the decision to link a spec whose `prds.outcome` **a human
settled**. `linkedOutcomeIsSettled` opens `if (!prdId) return { settled: false }`.

Live: **seven of the eight due rows carry `prd_id = NULL`.** The eighth links a spec whose
`outcome IS NULL`. All eight drafts came back at **confidence 1.0** - the 0.75 floor was never
reached, and is irrelevant. **Not one decision in production can satisfy that gate.** The mechanism
is on, spending money, and structurally unable to produce its output.

### The second, independent finding: the log has never had a scheduled writer

`forecast_resolution_log` is empty because **no scheduled path has ever written to it.** Two writers
exist: the human reopen path (`forecast.functions.ts:379`) and the `learning.record` tool
(`registry.server.ts:6179`, added today). `auditDueForecasts` never touches it, nor does the human
desk, nor MCP. **Even a tick that settled all seven would leave it at zero.** Its emptiness is not
evidence about the tick; the two facts are unconnected.

### What "1 row" actually means

pg_cron reporting the SQL statement's row count. The command is
`SELECT net.http_post(...) AS request_id;` and `net.http_post` is **asynchronous**: it enqueues and
returns one request id. So "1 row" = *one HTTP request id was minted*.

Read the clocks: the cron run **finished at 06:00:00.737**; the handler's `job_runs.started_at` is
**06:00:05.596**. The success was recorded **4.9 seconds before the handler began.** A non-2xx, a
timeout, or a Worker that never woke would all read `succeeded / 1 row` identically.

Worse: the handler's own response body carries `forecastsDrafted: 8, forecastsAutoSettled: 0` and
**it is discarded and stored nowhere**. A run that drafts 8 and settles 0 is byte-identical in every
observability surface to one that settles 8. Third instance of this class (`withJobRun` 2026-08-14,
F-171 2026-08-31).
