# Agent-to-agent contract

> _Created: 2026-08-22 · Last updated: 2026-08-22_

**The invariant: an external agent reaches Supaprod through three doors, and only one of them is the product.** `POST /api/mcp` is the product surface. `/mcp` is the OAuth front door and serves four tools. `/api/public/a2a/*` is the A2A surface and serves three skills. All three read the same `mcp_tokens` bearer credential except `/mcp`, which does not.

This file states what an external caller can and cannot do, cell by cell, and where each claim is enforced. It is the missing section of [`../docs/planning/initiatives/agent-first-platform.md`](../docs/planning/initiatives/agent-first-platform.md), which covers the human and internal-agent halves of the same design and gives this one a paragraph.

**Everything below carries a `file:line` or a production query run on 2026-08-22.** Where a claim in another live document disagrees, §7 names it.

**Source-to-live check.** The deployed commit is `1d7fe92` (Lovable `get_project`, 2026-08-22T14:16Z). It is an ancestor of local `HEAD`, and no commit since it touches `src/routes/api/mcp.ts`, `src/lib/mcp-protocol.ts`, `src/lib/mcp.functions.ts` or `src/lib/a2a-card.ts`. So the source read here is the source running in production.

## 1. The three doors, reconciled

### What each one is

| | **`POST /api/mcp`** | **`/mcp`** | **`/api/public/a2a/*`** |
| --- | --- | --- | --- |
| Built by | hand, `src/routes/api/mcp.ts:432` | `@lovable.dev/mcp-js`, `src/routes/mcp.ts:12` | hand, `a2a.message.send.ts:94` |
| Auth | bearer `slug:secret`, sha256 of the secret matched against `mcp_tokens.secret_hash` (`mcp.ts:496-510`, `validateToken` `:96`) | Supabase OAuth issuer, RFC 8414 discovery (`src/lib/mcp/index.ts:19-22`) | the **same** `mcp_tokens` bearer, via the shared `mcp-auth.server.ts` (`a2a.message.send.ts:3-8`) |
| Tools | **12 read** (`MCP_READ_TOOL_NAMES`, `mcp-protocol.ts:208`) + **6 governed write** (`MCP_WRITE_TOOL_NAMES`, `:404`) | **4 read**: `whoami`, `list_workspaces`, `list_decisions`, `search_signals` (`src/lib/mcp/index.ts:23`) | **3 skills**: `discovery.search_signals`, `discovery.ingest_signal`, `knowledge.export_skillpack` (`SKILL_TO_TOOL`, `a2a-protocol.ts:81-85`) |
| Protocol | JSON-RPC 2.0, three negotiated versions (`SUPPORTED_PROTOCOL_VERSIONS`, `mcp-protocol.ts:31`); a pinned version we cannot speak is a 400 (`mcp.ts:466-481`); notifications get 202 and no body (`:455-460`) | whatever the generator emits | JSON-RPC 2.0, `message/send`, `message/stream` (SSE), `tasks` |
| Rate limit | per token, `checkRateLimit` (`mcp.ts:562`), refusal carries `Retry-After` **and** a stable string code (`:610-627`) | not ours | same limiter, shared module |
| Retry safety | `idempotency_key` on every write, scoped `mcp:<tool>` × `<workspace>:<key>` (`dispatchWriteTool`, `mcp.ts:347-383`) | none | none |
| Audit | every call to `api_calls` via `logMCPCall` → `log_api_call` (`mcp.functions.ts:154`) | none of ours | same `logMCPCall` |
| Writes | 6, each behind its own scope **and** the global gate | none | 1 (`ingest_signal`), `WRITE_SKILL_IDS` `a2a-protocol.ts:87` |

Verified live against `https://supaprod.ai` on 2026-08-22:

```
POST /api/mcp  (no token) -> 401 {"jsonrpc":"2.0","error":{"code":-32003,"message":"Missing bearer token"},"id":1}
POST /mcp      (no token) -> 401 {"error":"unauthorized"}          # not JSON-RPC shaped
GET  /.well-known/agent.json -> 200 application/json
GET  /api/public/a2a/tasks   -> 200, three skills
GET  /api/public/ard/schema  -> 200 application/schema+json, 8498 bytes
```

### Two more public doors that carry no `mcp_token`

- **`POST /api/public/ingest-signals`** (`ingest-signals.ts:44`) — signal ingest for Zapier, a Slack outgoing webhook, a script. Authenticated by a **different** token table, `ingest_tokens`, not `mcp_tokens`. Production holds **0 rows** in it.
- **`GET /api/public/ard/schema`** (`ard.schema.ts:14`) — the published JSON Schema for the Outcome Contract. Unauthenticated by design, so an external tool can generate a valid ARD without our internal Zod types.
- **`POST /api/public/teardown`** (`teardown.ts:102`) — unauthenticated, IP-rate-limited at 10/day, and it spends real money: it runs a model call on the platform's own account (`:139-148`, `:183`).

### The recommendation: keep both, and it is not a close call

**`/api/mcp` is the product surface and must stay.** Everything the governance model depends on is implemented in that file and nowhere else: per-token capability scopes, the global write gate, call-time re-checking of both, idempotent writes, the typed rate-limit refusal, and the audit row. None of it exists on `/mcp`, and none of it can be moved there — `src/routes/mcp.ts:1-2` and both `[.mcp]/` route files carry the banner **"AUTO-GENERATED by @lovable.dev/mcp-js — do not edit. Regenerated by the Vite plugin."** Absorbing the hand-built surface into the generated one means taking ownership of the generated files by deleting that banner, and then maintaining a fork of somebody else's generator on the path that holds our write authorization.

**`/mcp` should stay too, and shrink to one job: being the OAuth front door.** It answers the one thing `/api/mcp` cannot. Today a machine cannot obtain a Supaprod credential: `issueMCPToken` (`mcp.functions.ts:56`) is a server function behind `requireSupabaseAuth`, reachable only from `_authenticated.settings.tsx:646` — a person, in a browser, clicking. `/mcp` already speaks RFC 8414 discovery against the Supabase issuer. That is the seam through which a token could be minted without a human, and it is the only one we have.

**So: two doors, different jobs, and the drift between them is the thing to fix.** The failure is not that both exist; it is that they overlap on exactly one tool (`search_signals`) with different semantics, and that the published discovery documents describe neither correctly. A2A is not a third door in any architectural sense — it is a narrow re-projection of `/api/mcp` over three of its eighteen tools, sharing the same token table, the same limiter and the same audit path. It should be described that way rather than as a peer.

**What has to change either way**, and it is small:

1. **Derive the agent card from the catalog.** `a2a-card.ts:81-93` hardcodes 10 read tools and 1 write tool. The catalog holds 12 and 6. The card is the one artifact whose entire job is being followed by a machine, and the same file's own comment (`:45-68`) records the last time it pointed a machine at the wrong endpoint. `public/agents.txt` carries the identical stale list.
2. **Give the two doors one description of themselves.** `/mcp` returns `{"error":"unauthorized"}` — not JSON-RPC, so a client that reached the wrong door cannot tell what happened.

## 2. The tool contract on the four primitives

Mapped onto Question → Bet → Run → Verdict as defined at [`agent-first-platform.md`](../docs/planning/initiatives/agent-first-platform.md) §2.1. Every tool named is on `/api/mcp`; the scope column is the `mcp_tokens.scopes` entry from `WRITE_SCOPE_BY_TOOL` (`mcp-protocol.ts:224-248`).

| Primitive | An external agent can READ | An external agent can WRITE | It cannot do at all today |
| --- | --- | --- | --- |
| **Question** | `search_signals`, `search_opportunities`, `search_prds`, `get_roadmap`, `get_governing_decision`, `get_contradiction_history` | `ingest_signal` (`write:signal`) — lands a `signals` row, injection-screened | Read or write a **theme**, an **insight** or an **assumption**. Score or re-rank an opportunity. Move one between now/next/later. Close a Question. |
| **Bet** | `search_decisions` (with standing/superseded outcome applied, `applyDecisionOutcomes` `mcp.functions.ts:268`) | `record_decision` (`write:decision`) → status `pending`, `source_kind: 'mcp'` (`mcp.functions.ts:805-811`) · `record_forecast` (`write:forecast`) → set-once, all three parts, horizon must be future (`:979-1016`) | **Attach a forecast in the same call that records the decision.** Record a rejected alternative — the field does not exist on this tool. Approve its own decision. Revise a forecast. |
| **Run** | nothing | nothing | **Everything.** No tool on any door names a mission, a track, a run or a step. See §3. |
| **Verdict** | `outcome_history`, `get_prd`, `get_ard`, `export_skillpack`, `list_due_forecasts` | `settle_outcome` (`write:outcome`) → `applyOutcome`, refuses to overwrite a settled verdict when the caller is an agent (`:911-948`) · `settle_forecast` (`write:forecast_resolution`) → refusal is in the `WHERE` clause so it cannot be raced (`:1050-1065`) | Write the edge back to the Bet. `learnings.decision_id` exists (migration `20260819181000...sql:205`) and `applyOutcome` does not set it (`outcome.functions.ts:591-599`); **0 of 133 learnings rows carry one.** |

Two notes the table cannot hold.

**`draft_spec` (`write:spec`) sits between Bet and Run and causes neither.** It lands a `prds` row at `status: 'draft'` (`mcp.functions.ts:857`). The reactor that turns a spec into work fires only on `approved` (`reactor_fanout_prd_approved`, migration `20260606150319...sql:128-130`), so a spec drafted through the API waits for a person.

**The read half is genuinely good and the write half is genuinely governed.** Neither is the problem. The problem is the column that is empty.

## 3. A Run is not driveable headlessly, and for an external caller it is worse than §1.2 says

[`agent-first-platform.md`](../docs/planning/initiatives/agent-first-platform.md) §1.2 records that six of seven stations run with `missionId: null`, so a steer aimed at any of them had nowhere to land. **That is a statement about steering something that is already running, and it has since been fixed** — the steer consumer now falls back to the track when there is no mission (`steerTarget`, `src/lib/ai/loop.server.ts`, in the `if (steerTarget && runId)` block; the argument is in the comment above it). Every station has a track; only Build has a mission. So all seven are steerable now.

**None of that reaches an external caller.** Every writer of a `steer` row into `agent_messages` is a server function — `steerStudioSession` (`studio.functions.ts:1141`) and the track equivalent (`spine/track.functions.ts:1043`). No MCP tool and no A2A skill writes one.

For an external caller the constraint binds one step earlier. There is no tool to start a Run. Grepped across the whole machine surface — `mcp-protocol.ts`, `mcp.functions.ts`, `a2a-protocol.ts` — the words `mission`, `spine_track`, `agent_runs`, `advanceMission` and `driveTrack` appear only inside comments. Not one of the 18 MCP tools or 3 A2A skills reaches an orchestration table.

So, after an external agent commits a Bet:

| It wants to | Today |
| --- | --- |
| Start the work | **Impossible.** No create tool on any door. |
| Watch the work | **Impossible.** No run, step or trace read tool. `api_calls` records only the agent's own calls. |
| Steer the work | **Impossible.** The mechanism now works for all seven stations; there is no tool that reaches it. |
| Stop the work | **Impossible over the API.** `stopRun` shipped (`src/lib/agent-runs.functions.ts:137`) and is a server function, not a tool. |
| Know the work finished | **Only by polling** `search_prds` or `outcome_history` and diffing. No callback, no webhook out, no push. The agent card says so: `capabilities.push_notifications: false` (`a2a-card.ts:117`). |

**There is exactly one indirect path from an API call to autonomous work, and it is the signal.** `ingest_signal` inserts into `signals`, which fires the `signals_reactor_fanout` trigger (migration `20260606150319...sql:147`), which enqueues an `event_queue` row for every enabled `signal.created` subscription in that workspace. Production holds 6 such subscriptions, all `enabled`, all at `approval_mode: 'auto'`, all targeting `discovery-scout`:

```sql
SELECT event_type, approval_mode, target_agent_slug, enabled, count(*)
FROM event_subscriptions GROUP BY 1,2,3,4;
-- signal.created      | auto    | discovery-scout | t | 6
-- opportunity.scored  | confirm | strategist      | t | 6
-- prd.approved        | confirm | orchestrator    | t | 6
```

So the one write that causes work fires an agent with no human in the loop at the trigger step, and the write a person would most want to see — `record_decision` — causes nothing at all. That is the wrong way round, and it is the single most useful thing to change about this surface.

**What "driveable" would minimally require**, in the order that unblocks the most: a `start_run` write tool carrying its own scope; a `get_run` read returning status, current station and the step list; then `stop_run` and `steer_run` promoted from server functions to tools. The last two are now the cheapest of the four, because the mechanism beneath both already works — only the door is missing.

## 4. Governance parity

**The approval policy engine does not run on this path.** `resolveToolMode` (`src/lib/ai/loop.server.ts`) has exactly two callers repo-wide: the internal agent loop in the same file, and `crew.functions.ts` where the UI shows a user what the policy would decide. The MCP route never calls it. Neither does A2A. _(Cited by symbol, not line: `loop.server.ts` moved under an active edit while this was being written.)_

So the two callers are governed by different machinery for the same act:

| | **UI / internal agent caller** | **MCP / A2A caller** |
| --- | --- | --- |
| Who decides the mode | `resolveToolMode` — per-agent stored mode, then risk floors, then trust-ramp ceilings | nobody; there is no mode |
| Can it queue an approval | yes, `agent_approvals` | **no** — a governed write either happens or is refused, in the same request |
| What gates it instead | the mode: `auto`, `confirm`, `review` | the token's scope **and** the global `interop_write_enabled()` gate, both re-checked at call time (`mcp.ts:702-731`) |
| What bounds the damage | the approval queue | **status floors**: a decision lands `pending`, a spec lands `draft`, a settled verdict cannot be overwritten by an agent |

**This is a defensible design, and it is not the same policy.** The status floors are a real guardrail — an agent proposes and a person disposes — but they are a *different* guardrail from the one the UI applies, and the difference is not written down anywhere before this file. A token holding `write:decision` performs, without any approval, an act that inside the product is a policy decision.

**Three specific parity defects.**

**1. The external `record_decision` accepts what the internal `decision.record` refuses.** As of **today**, `registry.server.ts` requires of every internally recorded decision: a `rationale` (min 1), **at least one rejected alternative**, and **all three forecast parts**, with the refusal text spelled out at `FORECAST_REQUIRED` — *"A decision with no forecast is an opinion, not a bet."* The MCP tool's schema (`recordDecisionSchema`, `mcp.functions.ts`, catalogued at `mcp-protocol.ts:282-294`) requires **`title` only**. `rationale` is optional, `alternatives_considered` does not exist as a field, and no forecast field exists. The door that was tightened this morning and the door left open are the same act on the same table.

The forecast can still be attached — but in a **second** call, under a **different** scope (`write:forecast`), which a token may not hold, on a decision that the first call already committed. The moat argument is that the forecast is captured at the moment of the call; on this path there are two moments.

**2. `interop_write_enabled()` is global, not per-workspace.** It reads a single `app_settings` row (migration `20260625140000_interop_write_scopes_gate.sql:64-75`). Six tool descriptions call it *"the workspace's outward-write gate"* (`mcp-protocol.ts:270, 284, 298, 312, 332, 353`). It is one switch for the entire deployment. One flip opens outward writes for every workspace at once, and the only per-workspace control is which tokens exist.

**3. A refused write is audited as a success.** `recordDecision` returns `{status: "quarantined", id: null}` **without throwing** when the injection screen quarantines the text (`mcp.functions.ts:795`; same shape at `:845`, `:997`, `:1040`). `runWriteTool` wraps that in `{success: true}`, and the route logs `result: "success"` with `write: true` (`mcp.ts:744`). The audit row does not record the returned status and does not record the row id. So `api_calls` cannot distinguish *"wrote a decision"* from *"refused the text and wrote nothing"* — which is exactly the question the audit trail exists to answer.

## 5. A worked loop, end to end

An external agent doing one real pass. Each step names the call and says whether it works today.

| # | Step | Call | Today |
| --- | --- | --- | --- |
| 1 | Find the door | `GET /.well-known/agent.json` | **Works.** Served from `src/server.ts:306`. But it advertises 10 read tools and 1 write tool against a catalog of 12 and 6, so an agent that plans from the card never learns `record_forecast` exists. |
| 2 | Get a credential | — | **Impossible without a person.** `issueMCPToken` (`mcp.functions.ts:56`) is behind `requireSupabaseAuth` and surfaced only at `/settings?section=interop` (`_authenticated.settings.tsx:646`; `/integrations` redirects there, `_authenticated.integrations.tsx:12`). A human logs in and clicks. |
| 3 | Handshake | `initialize`, then `tools/list` | **Works.** Version negotiated (`mcp.ts:642-651`). The catalog is filtered to what this token may actually call (`toolsForScopes`, `mcp-protocol.ts:422`), so a read-only token never discovers a write tool. |
| 4 | Discover a Question | `search_opportunities` / `search_signals` / `get_roadmap` | **Works.** |
| 5 | Read what was already decided | `get_governing_decision`, `get_contradiction_history`, `search_decisions` | **Works**, and this is the strongest part of the surface. |
| 6 | Commit a Bet | `record_decision` + `write:decision` | **Works.** Lands `pending`, `source_kind: 'mcp'`. Accepts a bare title — see §4.1. |
| 7 | Attach the forecast | `record_forecast` + `write:forecast` | **Works, but as a second call under a second scope.** Set-once; a horizon in the past is refused. If the token lacks `write:forecast` the Bet stands permanently forecast-less, because the field is immutable after the fact. |
| 8 | Start the work | — | **Impossible.** §3. The nearest available act is `ingest_signal`, which triggers `discovery-scout`, which is not the work the Bet called for. |
| 9 | Watch it | — | **Impossible.** §3. |
| 10 | Steer or stop it | — | **Impossible.** §3. |
| 11 | Find out it shipped | poll `search_prds`, diff | **Works, badly.** No push. |
| 12 | Read the Verdict | `outcome_history`, `get_ard` | **Works.** |
| 13 | Settle the outcome | `settle_outcome` + `write:outcome` | **Works**, and reaches the same `applyOutcome` the human path calls, which is why a verdict written here re-ranks the same way. The evidence and stakes scores are written as zero on purpose, because no classifier ran (`mcp.functions.ts:935-946`). |
| 14 | Grade the forecast | `list_due_forecasts`, then `settle_forecast` + `write:forecast_resolution` | **Works.** Third scope. Refusal to overwrite is in the `WHERE` clause. |
| 15 | Join the Verdict back to the Bet | — | **Not written.** `learnings.decision_id` exists and nothing populates it. |

**The shape of it: an external agent can read the whole loop, can state a bet, can grade a bet, and cannot do a single thing between those two.** Steps 8 through 10 are the product.

## 6. What production says, 2026-08-22

Run through the Lovable MCP against project `371dd588-1b70-4629-9bb5-9f003f3af373`. The queries are here so the numbers can be re-checked.

```sql
SELECT count(*) FROM mcp_tokens;                    -- 3
SELECT count(*) FROM api_calls;                     -- 7
SELECT public.interop_write_enabled();              -- true
SELECT count(*) FROM decisions WHERE source_kind='mcp';  -- 0
SELECT count(*) FROM ingest_tokens;                 -- 0
```

**The gate is open, and nothing on the record says a person opened it.**

```sql
SELECT key, value, updated_at, updated_by FROM app_settings
WHERE key IN ('interop_write_enabled','credits_enabled');
-- credits_enabled       | true | 2026-06-21 21:04:05+00 | 9e7958c5-3560-4133-ad83-0f8c42f1b33d
-- interop_write_enabled | true | 2026-08-10 13:10:05+00 | NULL
```

`admin_set_interop_write_enabled` raises unless `has_role(auth.uid(),'admin')` and then writes `updated_by = auth.uid()` (migration `20260625140000...sql:80-96`), so it cannot produce a NULL. The row was written by direct SQL with no auth context — the same route by which the three tokens were minted around the validator, nine minutes later. **The switch governing every outward write for the whole deployment has been on for twelve days and the record cannot name who turned it on.** Whether it should be on is a founder call; that it is on by accident is the finding.

**The three tokens are probes and none of them is live.**

```sql
SELECT slug, scopes, created_at, revoked_at, last_used_at FROM mcp_tokens ORDER BY created_at;
-- lane1-e2e-probe    | {write:decision,write:spec} | 13:19:14 | 13:21:01 | NULL
-- lane1-live-probe   | {write:decision}            | 13:37:06 | 13:39:15 | NULL
-- lane1-write-journey| {write:decision}            | 15:14:29 | 15:15:39 | NULL
```

All three created and revoked on 2026-08-10, each inside two minutes, all in the seed workspace `10000000-0000-4000-8000-000000000000`.

**`last_used_at` is NULL on all three despite seven logged calls, because nothing writes it.** No statement anywhere in `src/` sets `mcp_tokens.last_used_at`; `validateToken` (`mcp.ts:96-152`) is a `SELECT` only. The column is a token-hygiene signal that will read NULL forever.

**Seven calls, and the write path did fire once.**

```sql
SELECT tool_name, result, error_message, metadata, created_at FROM api_calls ORDER BY created_at;
-- tools/list      | success           |                                              | 13:37:20
-- tools/call      | error             | Unknown tool: record_decision                | 13:37:45
-- search_decisions| success           |                                              | 13:37:47
-- tools/list      | success           |                                              | 15:14:43
-- tools/list      | success           |                                              | 15:14:45
-- record_decision | success           | {"write":true}                               | 15:15:01
-- settle_outcome  | permission_denied | Token is missing the required scope: write:outcome | 15:15:03
```

Read this carefully. **The scope check works** — `settle_outcome` was refused for the exact right reason and audited as `permission_denied`. **The write path returned success once**, and yet `SELECT count(*) FROM decisions WHERE source_kind='mcp'` is **0**, and the seed workspace's 8 decisions all predate the call by three weeks. Per §4.3, a quarantined write is audited as `success`, so the audit trail cannot say whether that call wrote a decision that was later deleted or refused the text and wrote nothing. **That is the finding, not the ambiguity: an audit row that cannot answer "did this write happen" is not an audit row.**

**The meter has never metered.** `api_calls` carries `input_tokens`, `output_tokens` and `cost_usd`; `logMCPCall` passes `|| 0` for all three (`mcp.functions.ts:159-161`) and the route passes none. All 7 rows are zero. No MCP tool makes a model call, so nothing is being lost — but the columns claim a metering that does not exist, and `CallSurface` (`runtime.server.ts:356-373`) has no `mcp` literal, so these calls are outside the runtime chokepoint entirely.

**Corrected against the recorded state.** [`agent-first-platform.md`](../docs/planning/initiatives/agent-first-platform.md):1057 records *"0 tokens issued, 0 API calls ever."* The live answer is **3 tokens, 7 calls, one successful governed write, one correct scope refusal, and the write gate open.** Nothing has connected since 2026-08-10, and no token issued through the product UI has ever existed.
